# LAB3 — DL-04 RAG System Development I (ฉบับภาษาไทย)

> ฉบับภาษาอังกฤษ: [`README.md`](README.md) — เนื้อหาและตัวเลขตรงกันทั้งสองฉบับ

ระบบ RAG เต็มรูปแบบบนฐานความรู้เรื่องภัยหลอกลวงออนไลน์ภาษาไทย ประกอบด้วย hybrid retrieval
(BM25 + dense รวมผลด้วย RRF), การจัดอันดับใหม่ด้วย cross-encoder, การแปลงคำถาม (query transformation),
การสร้างคำตอบด้วย LLM พร้อมอ้างอิงแหล่งที่มา, หน่วยความจำบทสนทนา และชุดประเมินผลการค้นคืนที่เขียนสูตร
เมตริกขึ้นเองทั้งหมด

โครงสร้างรายวิชามาจาก
[aproot-en/Advanced-Topic-in-Computer-Software-Course](https://github.com/aproot-en/Advanced-Topic-in-Computer-Software-Course/tree/main/DL-04-RAG%20System%20Development%20I)
ส่วนฐานความรู้เขียนขึ้นใหม่สำหรับแล็บนี้ — ดูหัวข้อ [ฐานความรู้](#ฐานความรู้)

## มีอะไรใหม่จาก LAB2

LAB2 (DL-03) จบที่ dense retrieval ทุกอย่างใต้เส้นนั้นเป็นของใหม่ในแล็บนี้

| ขั้น | โมดูล | สถานะใน LAB2 |
|---|---|---|
| **Stage 1** — ไปป์ไลน์หลัก | `document_loader`, `text_splitter`, `embedding_model`, `vector_store`, `retriever` | เหมือน LAB2 |
| **Stage 2** — คุณภาพการค้นคืน | `hybrid_retriever` (BM25 + RRF), `rerankers` (cross-encoder), `query_transform` (rewrite / multi-query / HyDE), `index_meta` | ใหม่ |
| **Stage 2** — การสร้างคำตอบ | `prompt_templates`, `generator` (Ollama / OpenAI / Gemini), `memory`, `rag_pipeline` | ใหม่ |
| **Stage 2** — การประเมินผล | `metrics`, `build_golden_set`, `eval_retrieval`, `eval_generation` | ใหม่ |

## ไปป์ไลน์

```
scam_q_a.txt  ->  extracted_text.json  ->  chunks.json  ->  embeddings.npy  ->  document.index
  ฐานความรู้         lab01 extract          lab02 chunk      lab03 embed        lab04 vector DB
                                                                          +->  bm25_index.pkl

query -> query_transform -> hybrid retrieval -> rerank -> generator -> answer + [n] citations
         rewrite/multi/HyDE   BM25 + dense + RRF   cross-encoder   LLM        memory เก็บบริบทต่อเนื่อง
```

ทุกลูกศรหลัง `query` เป็นสวิตช์ใน `config.py` จึงปิดแล้ววัดผลได้จริง ไม่ต้องเถียงกันด้วยความรู้สึก

## ฐานความรู้

`data/scam_q_a.txt` — **คำถาม/คำตอบภาษาไทย 391 คู่** เรื่องภัยหลอกลวงออนไลน์ ฟิชชิง และความปลอดภัย
ไซเบอร์ส่วนบุคคล เขียนขึ้นเองสำหรับโปรเจกต์นี้ ตัดเป็น **404 chunks** (`CHUNK_SIZE` 400 ตัวอักษร,
ซ้อนทับ 50 ตัวอักษร, ตัดเฉพาะคำตอบที่ยาว)

| หัวข้อ | จำนวนคู่ Q&A |
|---|---|
| ฟิชชิงและลิงก์อันตราย | 157 |
| แก๊งคอลเซ็นเตอร์และมิจฉาชีพทางโทรศัพท์ | 85 |
| บัญชี รหัสผ่าน และการยืนยันตัวตน | 73 |
| กฎหมายและสิ่งที่ต้องทำหลังถูกหลอก | 39 |
| มัลแวร์ แอปดูดเงิน และความปลอดภัยของเครื่อง | 22 |
| การลงทุนและคริปโตหลอกลวง | 15 |

ทุกหัวข้อเขียนไว้ **3 ระดับภาษา** เพราะความต่างตรงนี้คือสิ่งที่วัดคุณภาพการค้นคืนได้จริง

| ระดับภาษา | จำนวนคู่ | ตัวอย่างคำถาม |
|---|---|---|
| ทางการ | 180 | `กดลิงก์ปลอมไปแล้วต้องทำอย่างไร` |
| พูดคุยทั่วไป | 109 | `เผลอกดลิงก์ในเอสเอ็มเอสไปแล้ว ซวยไหม` |
| ภาษาแสลง | 102 | `กูเผลอกดลิงก์เหี้ยนั่นไปแล้ว ตายป่ะ` |

ทั้งสามระดับให้ข้อเท็จจริงเดียวกันด้วยถ้อยคำต่างกัน คำถามที่พิมพ์แบบที่คนพิมพ์กันจริง ๆ จึงยังต้อง
ไปถึงคำตอบที่ถูกต้องให้ได้ นี่คือเส้นแบ่งระหว่างตัวจับคีย์เวิร์ดกับตัวค้นคืนจริง — และผลประเมินด้านล่าง
ยืนยันว่าเส้นแบ่งนี้มีอยู่จริง

เนื้อหาเฉพาะบริบทไทยเป็นความตั้งใจ: สายด่วน 1441, การแจ้งความออนไลน์, ความรับผิดของบัญชีม้า และอำนาจ
อายัดบัญชีฉุกเฉินตาม พ.ร.ก. อาชญากรรมทางเทคโนโลยี พ.ศ. 2566

## สวิตช์คุณสมบัติ

อยู่ใน `config.py` ทั้งหมด และวัดผลได้ทุกตัวผ่าน `evaluation/`

| สวิตช์ | ค่าเริ่มต้น | ผล |
|---|---|---|
| `USE_HYBRID` | `True` | ใช้ BM25 ควบคู่ dense retrieval แล้วรวมผลด้วย RRF |
| `USE_RERANK` | `True` | cross-encoder `BAAI/bge-reranker-v2-m3` จัดอันดับ `CANDIDATE_K` ใหม่ วัดได้ **+6.3 % MRR แลกกับความหน่วง 323 เท่าบน CPU** |
| `USE_QUERY_TRANSFORM` | `False` | ให้ LLM เขียนคำถามใหม่/ขยายคำถามก่อนค้น วัดได้ **ทุกโหมดคะแนนต่ำกว่าการปิดสวิตช์** |
| `USE_MEMORY` | `True` | เก็บประวัติบทสนทนาไว้ตอบคำถามต่อเนื่อง |
| `USE_LLM` | `True` | ถ้า `False` จะคืนข้อความที่ค้นได้แทนคำตอบที่สร้างขึ้น |
| `SHOW_SOURCES` | `False` | พิมพ์รายการแหล่งอ้างอิง `[n]` ใต้คำตอบ |
| `SHOW_DEBUG` | `False` | พิมพ์คำค้นที่ถูกส่งเข้าไปจริงและเวลาที่ใช้ในแต่ละขั้น |

## ข้อผิดพลาดในโค้ดต้นแบบของรายวิชาที่แก้ไปแล้ว

พบข้อบกพร่อง 5 จุดระหว่างทำให้โปรเจกต์รันได้ และแก้ครบทั้ง 5 จุดในโฟลเดอร์นี้

| ไฟล์ | ข้อบกพร่อง | การแก้ |
|---|---|---|
| `src/generator.py` | `NoLLM` ตัดพรอมป์ด้วยตัวคั่นภาษาอังกฤษ `"reference data :"` และ `"Q of user"` แต่ `USER_PROMPT` เขียนเป็นภาษาไทย จึงหาตัวคั่นไม่เจอสักครั้ง ทำให้ **`USE_LLM = False` ตอบว่า `"ขออภัย ไม่พบข้อมูลที่เกี่ยวข้อง"` กับทุกคำถาม** และ `eval_generation` ได้อัตราปฏิเสธ 100 % | ย้ายหัวข้อทั้งสองไปเป็นค่าคงที่ `CONTEXT_HEADER` / `QUESTION_HEADER` ใน `prompt_templates.py` ให้ทั้งฝั่งสร้างพรอมป์และฝั่งแยกพรอมป์ใช้ตัวเดียวกัน จะได้ไม่หลุดจากกันอีก |
| `main.py` | บล็อกที่พิมพ์รายการแหล่งอ้างอิงถูกคอมเมนต์ทิ้งไว้ `SHOW_SOURCES` จึงไม่มีผลอะไรเลย และ `rag.show_settings()` ก็ถูกคอมเมนต์ไว้เช่นกัน | เปิดใช้งานกลับทั้งสองจุด |
| `evaluation/eval_retrieval.py` | `all_misses = misses` อยู่ในลูปคอนฟิก ทำให้ลิสต์ถูกเขียนทับทุกรอบ รายงาน "ค้นไม่เจอ" จึงเหลือแค่คอนฟิกสุดท้าย | เปลี่ยนเป็นสะสมผล และแต่ละแถวระบุชื่อคอนฟิกกำกับไว้ |
| `src/generator.py` | คีย์ตัวอย่างของ Ollama เขียนเป็นสตริงไทย `"ollama-ไม่ใช้-key"` ซึ่งถูกใส่ในเฮดเดอร์ `Authorization` ที่ OpenAI SDK เข้ารหัสเป็น ASCII จึงทำให้ **ทุกการเรียก LLM โยน `UnicodeEncodeError`** และ `Generator.generate()` ดักทุก exception แล้วถอยไปคืน `chunks[0]["answer"]` โดยที่ `print` เตือนก็ถูกคอมเมนต์ไว้ — สรุปคือ `USE_LLM = True` คืนข้อความที่ค้นได้แต่รายงานตัวเองว่าเป็นคำตอบที่สร้างขึ้น โดยไม่มีอะไรขึ้นจอบอกเลย | เปลี่ยนคีย์ตัวอย่างเป็น ASCII (`"ollama-no-key"`) และเปิดคอมเมนต์ log `[llm]` ทั้งสองบรรทัด เพื่อไม่ให้การถอยกลับเงียบได้อีก |
| — | บทเรียนนี้ไม่มี `requirements.txt` (ขณะที่ DL-03 มี) | เพิ่มให้ พร้อมเวอร์ชันที่ตรวจสอบบนเครื่องนี้แล้ว |

การปรับโปรเจกต์มาใช้ฐานความรู้ชุดนี้ยังต้องแก้ทุกจุดที่ผูกกับหัวข้อเดิมด้วย ได้แก่ `SOURCE_FILE` และ
`DISCLAIMER` ใน `config.py`, `SYSTEM_PROMPT` / `REWRITE_PROMPT` / `HYDE_PROMPT` ใน
`prompt_templates.py`, `SLANG_MAP` ใน `query_transform.py`, `TO_SLANG` ใน `build_golden_set.py`
และคำถามตัวอย่างใน lab05–07

## วิธีรัน

```bash

การสร้างคำตอบใช้ **Gemini (`gemini-3.5-flash`)** ผ่าน endpoint ที่เข้ากันได้กับ OpenAI ให้คัดลอก

```

`config.py` จะอ่านไฟล์นั้นด้วย `python-dotenv` และ `.env` อยู่ใน `.gitignore` คีย์จึงไม่หลุดขึ้น repo
ถ้าอยากกลับไปใช้โมเดลบนเครื่องให้ตั้ง `LLM_PROVIDER` เป็น `ollama` (ใช้ `llama3.1:8b` ไม่ต้องมีคีย์)
หรือใช้ `openai` พร้อม `OPENAI_API_KEY` ส่วนการประเมินการค้นคืนไม่ต้องใช้ LLM เลย

## หน้าเว็บ (Web interface)

`api.py` เอาไปป์ไลน์ตัวเดียวกับที่ `main.py` ใช้อยู่มาเปิดผ่าน HTTP ไม่ได้เขียนระบบ RAG ขึ้นใหม่อีกชุด
และเบราว์เซอร์ไม่ได้เรียก LLM เอง FastAPI ทำหน้าที่เสิร์ฟไฟล์ใน `web/` เป็น static และรับ 3 endpoint

| Endpoint | ทำอะไร |
|---|---|
| `GET /api/health` | บอกว่าโมเดลกับ index โหลดเสร็จหรือยัง ใช้ LLM ตัวไหน และสวิตช์ใน `config.py` ตอนนี้เป็นอย่างไร |
| `POST /api/ask` | `{question, session_id}` -> `{answer, sources, no_context, answered_by, model, elapsed, timings}` โดยเรียกผ่าน `RAGPipeline.ask()` |
| `POST /api/clear` | ล้างความจำบทสนทนาฝั่งเซิร์ฟเวอร์ของ session นั้น |

- **โหลดโมเดลครั้งเดียว** ฮุก `lifespan` ของ FastAPI สร้าง `RAGPipeline` ตอนเปิดเซิร์ฟเวอร์ และเรียก
  `index_meta.warn_if_stale()` ตรงนั้นด้วย แต่ละคำถามจึงไม่ต้องเสียเวลาโหลดใหม่ และถ้า index ไม่ตรงกับ
  ข้อมูลก็รู้ตั้งแต่ก่อนถามคำถามแรก
- **แยกความจำตามเบราว์เซอร์ ไม่ใช่ก้อนเดียวทั้งเซิร์ฟเวอร์** เพราะ `RAGPipeline` มี
  `ConversationMemory` แค่ก้อนเดียว เซิร์ฟเวอร์จึงเก็บความจำแยกตาม `session_id` แล้วสลับเข้าไปตอนถาม
  โดยมี lock กันชนกัน ตาราง session เป็นแบบ LRU จำกัดที่ `MAX_SESSIONS = 200` หน่วยความจำจึงโตไม่จำกัด
  ไม่ได้
- **LLM ถูกเรียกจากฝั่งเซิร์ฟเวอร์เท่านั้น** API key ไม่หลุดไปถึงเบราว์เซอร์ และคำถามถูกจำกัดที่
  `MAX_QUESTION_CHARS = 1000` ตัวอักษร ทุก error — เปิดระบบไม่สำเร็จ, ข้อมูลเข้าไม่ถูกต้อง, LLM ล้มเหลว
  — ตอบกลับเป็น JSON รูปแบบเดียวกันคือ `{"error": ...}`
- **ทุกคำตอบบอกได้ว่ามาจากไหน** ฟิลด์ `answered_by` แยก 4 กรณีที่เมื่อก่อนหน้าตาเหมือนกันหมดบนจอ:
  `llm` (โมเดลเขียนคำตอบจากเอกสารที่ค้นได้), `llm_refused` (ค้นเจอ chunk แต่โมเดลเลือกไม่ตอบ),
  `no_context` (ค้นไม่เจออะไรเลย ระบบจึงตอบว่าไม่รู้ แทนที่จะปล่อยให้โมเดลเดา) และ
  `fallback_context` (เรียก LLM ไม่สำเร็จ จึงแสดงข้อความที่ค้นได้ดิบ ๆ) หน้าเว็บแสดงค่านี้พร้อมชื่อ
  โมเดลและเวลาที่ใช้ — ทั้งหมด, ค้นหา, เขียนคำตอบ — เป็นป้ายใต้คำตอบแต่ละข้อ
- **`web/` เป็น HTML/CSS/JS ล้วน ไม่มีขั้นตอน build** มีปุ่มคำถามตัวอย่าง รายการแหล่งอ้างอิง `[n]`
  ใต้คำตอบ และแถบสถานะที่อ่านค่าจาก `/api/health`

สวิตช์ทุกตัวใน `config.py` มีผลกับหน้าเว็บเหมือนกับตอนรันบนบรรทัดคำสั่งทุกประการ — หน้าเว็บเป็นแค่
ส่วนหน้าของคอนฟิกชุดเดียวกัน ไม่ใช่คอนฟิกคนละชุด

## ผลการทดลอง

ทุกตัวเลขด้านล่างวัดบนเครื่องเดียว — Windows 11, Python 3.11.9, PyTorch บน CPU
(`torch.cuda.is_available()` เป็น `False` บนเครื่องนี้), Ollama รันบน GPU และใช้ `llama3.1:8b` เป็น LLM

ระบุไว้ว่าปรับสวิตช์ตัวไหนเพื่อให้ได้ผลนั้น ส่วน `config.py` ที่คอมมิตไว้ตอนนี้เปลี่ยนไปแล้ว — เปิด
`USE_RERANK = True` และใช้ `gemini-3.5-flash` — ตัวเลขด้านล่างจึงอธิบาย "สวิตช์" ไม่ใช่ค่าเริ่มต้นปัจจุบัน

### การค้นคืน (Retrieval)

`python -m evaluation.eval_retrieval` — 54 รายการใน golden set x คำถามได้ถึง 4 รูปแบบ = 216 คำค้น
รันด้วย `USE_RERANK = True` เพื่อให้มีแถวที่สี่ สามแถวแรกออกมาเท่ากันเป๊ะกับการรันแยกที่
`USE_RERANK = False` แสดงว่าตัว rerank ไม่ไปรบกวนแถวเหนือมัน

| คอนฟิก | hit@1 | hit@10 | MRR | nDCG@3 | มิลลิวินาที/คำค้น |
|---|---|---|---|---|---|
| dense_only | 0.7133 | 0.9867 | 0.8272 | 0.8390 | 12.5 |
| bm25_only | 0.9867 | 1.0000 | 0.9933 | 0.9951 | 4.9 |
| hybrid | 0.8200 | 1.0000 | 0.9063 | 0.9148 | 12.5 |
| hybrid+rerank | 0.9267 | 1.0000 | **0.9633** | **0.9626** | 4035.5 |

แยกตามรูปแบบคำถาม (MRR):

| คอนฟิก | verbatim | slang | partial | natural |
|---|---|---|---|---|
| dense_only | 0.8568 | 0.7083 | 0.8405 | 0.8216 |
| bm25_only | 1.0000 | 1.0000 | 0.9821 | 0.9907 |
| hybrid | 0.9167 | 0.9429 | 0.8750 | 0.9028 |
| hybrid+rerank | 0.9537 | **1.0000** | 0.9464 | 0.9722 |

อ่านตัวเลขเหล่านี้ได้ว่า:

- **hybrid ชนะ dense_only ทุกรูปแบบคำถาม และห่างมากที่สุดตรงจุดที่ควรห่างพอดี** บนคำถามภาษาแสลง
  dense_only ตกลงเหลือ MRR 0.7083 ซึ่งเป็นคะแนนแย่ที่สุดของมัน ขณะที่ hybrid ยังยืนที่ 0.9429 ดีขึ้น
  **+33 %** ภาษาแสลงคือจุดที่โมเดลเชิงความหมายไม่มีคลังคำร่วมกันให้ใช้ แล้วการจับคำตรง ๆ เข้ามาช่วย
  ซึ่งตรงกับสิ่งที่เอกสารรายวิชาทำนายไว้
- **hit@10 ขยับจาก 0.9867 เป็น 1.0000 เต็ม** ทันทีที่มี BM25 ร่วมด้วย พอใช้ hybrid แล้ว chunk ที่ถูกต้อง
  ไม่เคยหลุดออกจากชุดผู้สมัคร ตัว rerank จึงมีของให้จัดอันดับในทุกคำค้น
- **การ rerank ทำงานตรงตามที่เอกสารรายวิชาบอกไว้ทุกประการ** MRR 0.9063 -> 0.9633 (+6.3 %),
  nDCG@3 0.9148 -> 0.9626 (+5.2 %), hit@1 0.8200 -> 0.9267 (+13.0 %) — และ hit@10 ไม่ขยับเลย เพราะ
  cross-encoder ทำได้แค่จัดอันดับสิ่งที่ค้นเจอแล้วใหม่ ดึง chunk ที่พลาดไปแล้วกลับมาไม่ได้ มันจึงขยับ
  เฉพาะเมตริกที่ไวต่ออันดับ และไม่แตะเมตริกที่วัดการเป็นสมาชิกของชุดผล ยิ่งกว่านั้น hit@10 ที่นี่เต็ม
  1.0000 อยู่แล้ว จึงไม่มีที่ให้ขยับตั้งแต่ต้น การ rerank ยังปิดจ๊อบรูปแบบภาษาแสลงได้เต็ม
  0.9429 -> 1.0000
- **ตัว rerank กินเวลา 4035.5 มิลลิวินาทีต่อคำค้น เทียบกับ 12.5 มิลลิวินาทีของ hybrid — ช้ากว่า 323 เท่า**
  เพราะต้องให้คะแนนคู่คำถาม-เอกสาร 20 คู่ต่อคำค้นผ่าน cross-encoder ขนาด 568M พารามิเตอร์
  (`BAAI/bge-reranker-v2-m3`) รวม 4320 คู่ บน CPU มันแม่นที่สุดในบรรดาที่วัดมาและช้าที่สุดด้วย จึงเป็น
  การแลกที่ตั้งใจ: คอนฟิกที่คอมมิตเลือกเปิดมันและยอมรอ บนเครื่อง Mac ที่ใช้รันหน้าเว็บ การค้นแบบเปิด
  rerank ใช้เวลาราว 3–5 วินาที และมีเวลาเขียนคำตอบของ LLM บวกเพิ่มอีกไม่กี่วินาที
- **BM25 เดี่ยว ๆ ได้ 0.9933 ไม่ใช่ผลลัพธ์ แต่เป็นสัญญาณเตือน** ดูหัวข้อด้านล่าง

ขอแก้ตัวเลขจากตารางฉบับก่อน: ฉบับนั้นรายงาน hybrid ที่ 7.9 มิลลิวินาที/คำค้น เทียบกับ dense_only ที่
11.9 แล้วสรุปว่า hybrid ทั้งดีกว่า *และ* เร็วกว่า พอรันใหม่ทั้งคู่ออกมาที่ 12.5 เท่ากัน นั่นคือ noise
ของการจับเวลา และข้อสรุปนั้นผิด — hybrid ทำทุกอย่างที่ dense_only ทำ *แล้วค่อย* รัน BM25 ต่อ จึงเร็ว
กว่าไม่ได้ BM25 เดี่ยว ๆ ใช้ 4.9 มิลลิวินาที เล็กพอเทียบกับการค้นเชิงความหมายจนความต่างจมหายไปใน
ความแปรปรวนระหว่างรอบ

### การแปลงคำถาม (Query transformation)

`eval_retrieval.py` เรียกตัวค้นคืนโดยตรงและไม่ได้ผ่านขั้นแปลงคำถามเลย จึงวัดสวิตช์นี้ไม่ได้เลย
`evaluation/eval_query_transform.py` เขียนขึ้นมาเพื่อการนี้โดยเฉพาะ: มันทำแบบเดียวกับ
`RAGPipeline.search_only()` คือแปลงคำถามก่อน แล้วค้นด้วยทุกคำค้นที่ได้กลับมา พร้อมบันทึกว่าสิ่งที่ถูก
ส่งเข้าตัวค้นคืนจริง ๆ คืออะไร

54 รายการ x {natural, slang} = 68 คำค้นต่อโหมด, ใช้ `llama3.1:8b` บน Ollama, ปิด rerank
โหมด `none` ไม่ได้แปลว่า "ไม่ประมวลผลอะไรเลย" เพราะ `normalize_query()` ยังใช้ตารางเทียบคำแสลงอยู่
ซึ่งคือสิ่งที่ไปป์ไลน์ทำเป็นปกติเมื่อปิด `USE_QUERY_TRANSFORM`

| โหมด | hit@1 | hit@10 | MRR | nDCG@3 | มิลลิวินาที/คำค้น | จำนวนคำค้นที่ยิงจริง | ครั้งที่ LLM ปฏิเสธ |
|---|---|---|---|---|---|---|---|
| none | **0.8529** | 1.0000 | **0.9228** | **0.9251** | 25.0 | 1.00 | 0 |
| rewrite | 0.3529 | 0.8235 | 0.5364 | 0.5527 | 698.8 | 1.00 | 4 |
| multi_query | 0.7794 | 1.0000 | 0.8713 | 0.8739 | 2134.0 | 3.68 | 5 |
| hyde | 0.8088 | 1.0000 | 0.8881 | 0.8937 | 4414.0 | 2.00 | 18 |

แยกตามรูปแบบคำถาม (MRR):

| โหมด | natural | slang |
|---|---|---|
| none | **0.9028** | **1.0000** |
| rewrite | 0.5774 | 0.3782 |
| multi_query | 0.8704 | 0.8750 |
| hyde | 0.8715 | 0.9524 |

**ทั้งสามโหมดที่ใช้ LLM ได้คะแนนต่ำกว่าการปิดสวิตช์ทิ้งไว้** — rewrite -41.9 % MRR, multi_query
-5.6 %, hyde -3.8 % ซึ่งตรงข้ามกับที่เอกสารรายวิชาคาดไว้ สาเหตุมีสามข้อ และไม่มีข้อไหนแปลว่า
"การแปลงคำถามเป็นแนวคิดที่แย่"

1. **ชุดทดสอบให้รางวัลกับการคงถ้อยคำเดิมไว้ ส่วน `rewrite` ทิ้งถ้อยคำเดิมทั้งหมด** `rewrite`
   *แทนที่* คำถามด้วยสำนวนของ LLM (ยาวเฉลี่ย 69 % ของต้นฉบับ) ขณะที่ `multi_query` และ `hyde` เก็บ
   คำถามเดิมไว้เป็นคำค้นแรกแล้วค่อยเพิ่มคำค้นอื่นต่อ ลำดับนี้คือลำดับความเสียหายพอดี ตัวอย่างจริง:
   `การหลอกให้โอนตังค์ไป "บัญชีปลอดภัย" คืออะไร` ถูกเขียนใหม่เป็น
   `การหลอกลวงการโอนเงินไปยังบัญชีปลอม` ซึ่งทิ้งคำว่า `บัญชีปลอดภัย` — คำที่ chunk เป้าหมายสร้างขึ้น
   รอบ ๆ มันพอดี เมื่อ golden set สร้างคำถามจากตัวข้อความเป้าหมาย (ดูด้านล่าง) การเรียบเรียงใหม่ใด ๆ
   จึงเป็นการเสียคะแนนโดยโครงสร้าง
2. **โมเดลปฏิเสธที่จะตอบ** `llama3.1:8b` ผ่านการปรับจูนด้านความปลอดภัยมา ฐานความรู้พูดเรื่องกลโกง
   ทำงานอย่างไร และการสั่งให้มันแต่งคำตอบสมมติที่อธิบายเทคนิคหลอกลวง อ่านในสายตาโมเดลเหมือนการขอ
   ให้ช่วยไปหลอกคนอื่น **พรอมป์ HyDE 18 จาก 68 ครั้ง (26 %) ตอบกลับมาเป็นคำขอโทษ** แทนที่จะเป็น
   คำตอบสมมติ — `ขอโทษครับ/ค่ะ แต่ฉันไม่สามารถช่วยเขียนคำตอบที่อาจช่วยให้บุคคลหลอกลวง...` — และ
   `query_transform.py` ไม่มีทางแยกคำปฏิเสธออกจากคำตอบได้ คำขอโทษนั้นจึงถูกส่งเข้าตัวค้นคืนในฐานะ
   คำค้น ส่วน `rewrite` (4 ครั้ง) และ `multi_query` (5 ครั้ง) เจอน้อยกว่าแต่ก็เจอ นี่คือรูปแบบความ
   ล้มเหลวของ HyDE บนฐานความรู้ที่อ่อนไหวด้านความปลอดภัยซึ่งเกิดซ้ำได้จริง และจะมองไม่เห็นเลยถ้าไม่ log
   ว่าคำค้นที่ยิงออกไปคืออะไร
3. **`normalize_query()` ทำงานนั้นให้ฟรีอยู่แล้ว** ตารางเทียบคำแมป ตังค์ -> เงิน, แบงก์ -> ธนาคาร,
   มิจ -> มิจฉาชีพ ซึ่งก็คือการเชื่อมภาษาแสลงเข้าหาภาษาทางการที่ LLM ควรจะมาช่วยทำพอดี บนรูปแบบ
   ภาษาแสลง โหมด `none` ได้ MRR เต็ม **1.0000** อยู่แล้ว จึงไม่เหลืออะไรให้ได้เพิ่ม มีแต่ถ้อยคำให้เสีย

**เปอร์เซ็นต์เหล่านี้มี noise สูง ให้ดูทิศทาง ไม่ใช่ขนาดของตัวเลข** การทดลองนี้รันสองรอบด้วยโค้ดเดียวกัน
ที่ `LLM_TEMPERATURE = 0.2`

| โหมด | MRR รอบ 1 | MRR รอบ 2 |
|---|---|---|
| none | 0.9228 | 0.9228 |
| rewrite | 0.6130 | 0.5364 |
| multi_query | 0.8811 | 0.8713 |
| hyde | 0.8186 | 0.8881 |

`none` เป็น deterministic จึงซ้ำได้เป๊ะ ส่วนโหมดที่ใช้ LLM ขยับหมด โดย `hyde` ขยับถึง 8.5 จุด มากพอที่
การรัน 68 คำค้นรอบเดียวจะแยก `hyde` ออกจาก `multi_query` ไม่ได้ สิ่งที่ยืนได้ทั้งสองรอบและเป็นข้อสรุป
เดียวที่กล่าวอ้างที่นี่คือ ทั้งสามโหมดอยู่ต่ำกว่า `none` ตัวเลขที่คอมมิตไว้คือรอบที่ 2 ซึ่งคำค้นที่ผ่าน
การแปลงทั้งหมดถูกบันทึกไว้ใน `outputs/eval_query_transform.json`

- **การค้นคืนไม่พลาดเลยในชุดย่อยนี้ (1.00) ทุกตัวเลขที่เหลือจึงเป็นเรื่องของการสร้างคำตอบล้วน ๆ**
- **อัตราปฏิเสธ 10 % เป็นความล้มเหลวฝั่งสร้างคำตอบ ไม่ใช่ฝั่งค้นคืน** ทั้งสองรายการที่ถูกปฏิเสธมี

  `SYSTEM_PROMPT` อย่างเคร่งเกินไป
- **อัตราการอ้างอิง 0.90 เท่ากับ 1 − อัตราปฏิเสธพอดี** ทุกคำตอบที่เขียนออกมาจริงมี `[n]` กำกับในเนื้อ
  คำตอบ สองรายการที่ไม่มีคือสองรายการที่ปฏิเสธ ซึ่งไม่มีอะไรให้อ้างอิงอยู่แล้ว คำสั่งเรื่องการอ้างอิง
  จึงถูกทำตาม 100 % ในทุกกรณีที่มันมีผลบังคับ
- **faithfulness 0.8216** บอกว่าคำตอบเกาะอยู่กับข้อความที่ค้นได้ ไม่ได้ดึงความรู้ของโมเดลเองออกมาใช้
  ซึ่งเป็นคุณสมบัติที่สำคัญที่สุดสำหรับฐานความรู้ชุดนี้
- **correctness 0.6152 และ relevance 0.4475 เป็นฮิวริสติกนับคำซ้อนทับ ไม่ใช่การตัดสินคุณภาพ**
  `word_overlap()` นับว่ามีโทเคนของข้อความหนึ่งไปปรากฏในอีกข้อความกี่ตัว คำตอบที่ถูกต้องแต่ใช้ถ้อยคำ
  ต่างจากคำตอบอ้างอิงจึงได้คะแนนต่ำ และคำตอบที่ละเอียดก็ได้ relevance ต่ำเพราะความยาว ไม่ใช่เพราะผิด
  ให้อ่านสองค่านี้ว่า "ไม่หลุดประเด็น" ไม่ใช่ "ตอบถูก" การให้คะแนนความถูกต้องอย่างจริงจังต้องใช้ LLM
  เป็นกรรมการหรือให้คนอ่าน ซึ่งทั้งสองอย่างอยู่นอกขอบเขตของแล็บนี้

### ชุดประเมิน (golden set) รั่วคำตอบของตัวเอง

`build_golden_set.py` สร้างทุกรูปแบบคำถามจากคำถามต้นฉบับด้วยการดำเนินการกับสตริง แต่ละรูปแบบจึงคง
ถ้อยคำเดิมไว้เกือบทั้งหมด

| รูปแบบ | จำนวนรายการ | วิธีสร้าง |
|---|---|---|
| verbatim | 54 | ใช้คำถามเดิมทั้งประโยค |
| natural | 54 | `สงสัยว่า` + คำถามเดิม + ` ยังไงคะ` |
| partial | 28 | คำถามเดิมที่ตัด stopword ออก |
| slang | 14 | สลับศัพท์เฉพาะ/ศัพท์เทคนิคด้วยตาราง `TO_SLANG` |

BM25 จับคู่ที่ระดับโทเคน และเกือบทุกโทเคนของเป้าหมายยังอยู่ในคำถาม มันจึงค้น chunk ที่ถูกต้องขึ้นมา
เป็นอันดับหนึ่งได้แทบทุกครั้ง ส่วนรูปแบบ `natural` — ตัวที่เอกสารรายวิชาบอกว่าเป็นกรณีชี้ขาด — ก็คือ
คำถามเดิมที่เอาคำนำหน้ากับคำต่อท้ายมาแปะ ซึ่งไม่เปลี่ยนอะไรเลยสำหรับตัวให้คะแนนแบบ bag-of-words

ดังนั้นคอลัมน์ BM25 วัดว่าแต่ละวิธีรับมือกับ *สำเนาของเป้าหมายที่ถูกแก้เล็กน้อย* ได้ดีแค่ไหน ไม่ได้วัด
ถ้อยคำจริงของผู้ใช้ คอลัมน์ dense และ hybrid ยังให้ข้อมูลที่มีความหมายเมื่อเทียบกันเอง และรูปแบบภาษา
แสลงคือจุดเดียวที่ชุดทดสอบมีเขี้ยวจริง ซึ่งเป็นเหตุผลที่ช่องว่างระหว่าง dense กับ hybrid ถ่างออกตรงนั้น
การทำให้ชุดทดสอบทั้งชุดซื่อตรงจริง ๆ ต้องมีคำถามที่สื่อเจตนาเดียวกันแต่ไม่ใช้คลังคำร่วมกัน ซึ่งแปลว่า
ต้องเขียนคำถามด้วยมือหรือให้ LLM สร้างแล้วมีคนตรวจซ้ำ เพราะการเรียบเรียงใหม่ของ LLM เปลี่ยนความหมาย
ของคำถามได้แบบเงียบ ๆ

### สิ่งที่ตัวเลขชุดนี้ยังไม่ครอบคลุม

ตอนนี้ทุกสวิตช์ใน `config.py` มีผลวัดรองรับแล้ว สิ่งที่ยังขาดคือความลึก ไม่ใช่ความครอบคลุม

| ช่องว่าง | ทำไมจึงสำคัญ |
|---|---|
| `correctness` และ `relevance` เป็นฮิวริสติกนับคำซ้อนทับ | มันแยกคำตอบที่ถูกแต่ใช้คำต่างออกจากคำตอบที่ผิดไม่ได้ ถ้าจะให้คะแนนคุณภาพคำตอบอย่างถูกต้องต้องใช้ LLM เป็นกรรมการหรือให้คนอ่าน |
| การประเมินการสร้างคำตอบทำบน 20 รายการ รูปแบบเดียว รอบเดียว | พอจะจับได้ว่าไปป์ไลน์พัง แต่ไม่พอจะเทียบสองพรอมป์หรือสองโมเดล |
| การทดลองแปลงคำถามขยับได้ถึง 8.5 จุด MRR ระหว่างสองรอบที่เหมือนกันทุกอย่าง | ตัวเลขจาก LLM รอบเดียวมี noise มากกว่าความต่างส่วนใหญ่ที่กำลังวัดอยู่ |
| ทดสอบแค่ `llama3.1:8b` ตัวเดียว | อัตราปฏิเสธ HyDE 26 % เป็นคุณสมบัติของโมเดลตัวนี้บนหัวข้อนี้ ไม่ใช่ของ HyDE โดยทั่วไป |

## หมายเหตุ

- คำตอบถูกจำกัดให้อยู่ในฐานความรู้ด้วย `SYSTEM_PROMPT` ซึ่งบังคับให้อ้างอิง `[n]` ในเนื้อคำตอบ
  บังคับให้ตอบ `"ขออภัย ไม่พบข้อมูลที่เกี่ยวข้อง"` เมื่อบริบทที่ค้นได้ไม่เพียงพอ และให้เรียงขั้นตอน
  เร่งด่วนไว้ก่อนเมื่อผู้ถามเพิ่งเสียเงินไป ส่วน `DISCLAIMER` จะถูกต่อท้ายทุกคำตอบ
- `index_meta.py` เก็บลายนิ้วมือของชุดข้อมูลและการตั้งค่าการตัด chunk ส่วน `main.py` จะเตือนเมื่อ index
  ไม่ตรงกับสิ่งที่ใช้สร้างมันแล้ว ให้รัน `build_index.py` ใหม่หลังแก้ข้อมูลหรือแก้ค่าใด ๆ ใน
  `TRACKED_SETTINGS`
- ฐานความรู้ชุดนี้เป็นสื่อการเรียนสำหรับศึกษาการค้นคืนข้อมูล ไม่ใช่คำปรึกษาทางกฎหมาย หมายเลขสายด่วน
  และรายละเอียดข้อกฎหมายควรตรวจสอบกับแหล่งข้อมูลทางการที่เป็นปัจจุบันก่อนนำไปใช้จริง
